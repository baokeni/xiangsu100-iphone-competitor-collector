# 采集前的任务流程与分支规划

用于把研究问题转成可执行、可核验的用户任务。每轮正式走查前必须读本文件；规划不能等截图结束后补写。

## 前置产物与阶段核对

在任务准备目录创建可阅读的流程图、分支表和 `journey-plan.json`，从任务契约引用它。复用同一份节点与分支定义，避免文档和执行表各写一套。开始采集前主动展示：

1. 用户目标、起点、终点和具体情境；假设与用户已确认条件分开。
2. 采集对象、研究范围、只读/变更边界和成功标准。
3. 主路径、替代路径、详情展开、返回比较、修改取消和适用的异常恢复。
4. 每条分支解决的研究问题、触发条件、必要证据、返回后的状态。
5. 每个 App 的计划映射、待确认入口、已知阻塞和覆盖取舍。

核对资料是否足够，不要求用户重复批准已确认的条件。缺少会改变任务或授权的信息时先澄清；纯粹界面未知标记为采集中核验。研究计划完成不等于设备控制可用，也不等于这些路径已被观察。

## 文字与流程图一起交付

用户任务规划默认同轮交付两种表达（用户明确只要文字时除外）：

1. **文字任务/分支表**：说明用户意图、研究问题、观察点、必要证据和结束条件。
2. **可直接查看的流程图**：在回复中实际展示，优先使用可渲染的 Mermaid；环境不能渲染时，提供并展示可预览的 SVG/HTML/图片，同时保留可编辑源文件。不能只写一串箭头、只保存代码或仅附文档链接就算已经展示流程图。

图从用户目标出发，包含起点/终点、主路径、关键判断及条件标签、替代路径、按需展开与返回、改选/取消、适用的异常恢复和放弃。用圆角起止节点、矩形任务节点、菱形判断节点；分支箭头标清触发条件。需要时用实线表示主路径、虚线表示按需查看或返回，并配图例；线型不代表已经观察。

复杂流程先给可读总览，将细节放到分图，不把全部内容挤成无法辨认的一张大图。检查文字、连线方向、条件分支和回路，避免遮挡、裁切、无出口循环。每个判断应有合理去向，但不为补齐形状虚构产品能力。

流程图、文字表和 `journey-plan.json` 复用任务编号与节点/分支定义。图可合并同阶段任务，但须标对应编号；条件节点可使用独立ID并关联任务。用户调整范围后同步更新全部表达，保留“已规划/尚未观察”状态。共同流程是用户决策图，不是三个App都存在相同页面的证明。

用户给的参考图只借鉴表达结构；其中的支付、登录等节点不自动纳入研究。以当前确认范围为准删除无关节点。交付时先给简要文字说明，再展示图和关键分支；教学模式下继续保留用户修正/反馈入口，不自动推进到采集。

## 从用户问题推导分支

先画用户决策，再映射页面。按任务相关性检查：

- **发现路径**：直接浏览；先分类/筛选再浏览；知道关键词时搜索。不要把搜索当作自然入口失败后的自动替代证据。
- **详情展开**：主详情→评论列表→单条评论/图片；主详情→店铺→商家信息/环境/资质；必要时店铺菜单→同一餐品。用户主动提出的分支应前置列入。
- **执行与反馈**：选择/修改规格、取消、返回，分别检查价格、选中态与上下文。
- **不满意后的继续选择**：详情返回原列表，保留条件与位置；换一个候选继续比较。
- **异常恢复**：筛选后无结果、售罄、门店休息、加载失败、功能没有找到；先记录真实状态，再按范围恢复。
- **提前结束**：信息足够可以完成判断；需要未经授权的变更或遇到敏感页面则停止。不要为了覆盖图上的节点强制交易。

这些是检查维度，不是所有产品必有的页面。外卖例子不能强制套用到内容阅读、收藏管理等任务。

## 每条分支的最小记录

| 字段 | 要写清什么 |
|---|---|
| branch_id / title | 稳定编号与用户意图，如“通过评论核实餐品” |
| research_questions | 对应研究问题/预研假设的编号 |
| requirement | required_check：必须检查可达性，可安全到达则采集；conditional：仅条件满足时展开 |
| trigger / entry_state | 何时进入、从哪个状态分叉；目标餐品/门店标识来自本次实际画面 |
| planned_steps | 逐步操作意图和预期状态；不预填坐标或历史语义引用 |
| observations / evidence_required | 观察什么，哪些进入前、变化后与返回证据缺一不可 |
| exit_condition / return_to | 何时算完成，回到哪里、恢复什么条件或选中态 |
| fallback / stop | 不可达、失败、缺失、超范围时怎么处理 |

例如“详情→评论”还要说明评论列表入口、相关筛选、单条详情或图片是否可打开，以及返回时是否仍在原餐品。只写“看评论”不能指导完整采集。

## 逐 App 映射与覆盖状态

`journey-plan.json` 至少包含：`plan_version`、`scenario`、`nodes`、`branches`、`app_coverage`、`coverage_policy`。节点使用稳定 ID；分支可以共享节点。`app_coverage` 逐 App、逐 branch_id 登记 `status`、`actual_route`、`evidence`、`reason`。该文件是采集规划/覆盖记录，不改变最终报告 schema_version 2。

状态含义：

- `planned`：已规划，尚未走查。
- `observed`：实际路径及必要前后状态已经采集，附本轮证据引用。
- `partial`：只采到部分路径，说明缺少什么。
- `blocked`：设备、敏感页面、交易授权、地区或其他条件阻塞。
- `not_found_in_scope`：按登记的有限检查范围没有发现入口，不等于产品全局无此功能。
- `not_applicable`：实际产品结构或明确资料证明不适用，注明依据。
- `skipped`：因预算或范围决定未采，必须说明影响，不能标成不适用。
- `user_excluded`：用户明确移出本轮范围，注明决定来源；不自动补采。

新运行如要标记控制器 `completed`，将本轮 `journey-plan.json` 复制到 run 目录。`app_coverage[app_key].branches[branch_id]` 的 `observed` 项需有 `actual_route`、本轮文件路径组成的 `evidence`、与 `planned_steps` 等长的 `step_checks`。每个 step check 填 `status: observed`、本轮成功事件的 `event_sequences` 和这些事件关联的证据文件路径；若有 `return_to`，再填返回后的 `return_event_sequence`（成功的新 snapshot）和 `return_evidence`。未尝试、部分完成、受阻和用户排除要各自写真实状态；有理由的 `not_applicable` 还须本轮证据，`user_excluded` 须用户决定来源。验收器检查事件引用和文件存在，研究者仍须核对证据内容是否真实支持动作和返回结论。获准改动状态时，另在 run 目录保存 `rollback-review.json`，记录 `verified: true`、回滚后成功 snapshot 的 `event_sequence` 和其 `evidence` 文件路径。

App A 可能“列表→餐品详情→店铺”，App B 可能“列表→店铺菜单→餐品面板”。保持同一用户问题和实体，按实际结构记录。评论不存在独立详情页时可记录原位展开或图片预览。SKU 没有单独页面也记录其真实形态。某平台需要先付费才能看选配时停止，保留限制。

## 采集顺序与成本控制

采用有界的分支覆盖，不枚举所有路径组合：

1. 先保存公共入口与列表；分别观察直接浏览和筛选后的浏览，记录条件变化。
2. 在同一主样本餐品上，按实际路径串联评论、店铺和 SKU；每条分支回到可确认的父状态。
3. 再做一次返回列表、更换候选的比较，避免完整流程从首页重复。
4. 分类/筛选、规格优先选一个与任务相关且会产生可辨反馈的条件。遇到新机制或反例才扩展样本。
5. 异常状态只在发生或可安全自然触发时采集，不制造网络/账户异常，不刻意穷尽筛选。

范围和设备就绪后，一次授权连续执行；在共同父页面内完成相关分支及返回，再切换候选。阶段核对由 AI 内部主动完成，进度截图回传后继续，不等待用户反复说“继续”。只有确实依赖用户处理的步骤或未解决的授权/关键信息才暂停。

把截图留给新增的研究证据：首次关键页面、选择/价格/筛选等实质变化、必要的视觉返回比较、相关异常和回滚。普通加载、无变化的重复页面和纯导航不逐步截图。同一张图可以关联多个分支；进度文档和对话只展示代表性图，不反复嵌入。语义快照不足以判断或需要当前坐标定位时，仍获取新截图。去重依据页面、实体、价格、选项、筛选与位置等任务状态，不因时钟变化多采，也不把价格改变的同名页面当重复。

复用当前运行中仍有效的公共证据；实际动作后仍需新 snapshot，不复用失效引用。上一步的操作后快照直接作为下一步依据，不在操作前再读一次；截图与回传按关键状态触发，不绑定每一次动作。返回状态必须以本次新快照核验；旧图仅作上下文，需要视觉前后对比时仍保存返回新图。前置图只是操作意图，所有具体触点都来自当前证据。评论浏览与发布评论是不同动作，不能绕过安全策略；如果旧封装误拦浏览，记录工具阻塞并单独修正验证。

关闭会话前对照每条分支的 planned_steps 逐动作核对证据，特别是规格选择、再次修改、取消和返回；不要只看 observed 标签。安全且已授权的缺项在当前会话补齐，避免关闭后重新启动整条路线。用户取消的分支登记原因，不再追问或补采。

每个 required_check 都必须有最终状态和原因；可安全到达的必要分支应采集。尚有 planned/partial/blocked 等项时说明缺口及其对结论的影响，不声称完整覆盖。无法采到关键分支时缩小结论或补采，不能凭截图补写流程。

## 分析交接

先执行[精选截图 HTML 与复查](evidence-review.md)：完成精选/归档及来源映射，保存可直接打开的 HTML，并登记对应 App 的 evidence_review。用户要求先复查时，在该阶段交付后等待一次反馈；确认或明确要求直接分析后继续。当前已有合格 HTML 则复用，不另做一套。

采集结束后先核对覆盖记录与事件，再做任务对比、认知走查、信息架构和视觉分析。引用节点/分支编号可用来关联证据，但最终报告的 journey 只重建真实发生的步骤。单独说明替代路径、返回保留状态、失败恢复与未采分支；二维定位与建议不能超出实际证据。

## 获准查看支付页时的边界

若用户明确允许，只读路径可以延伸到订单确认或支付页，观察金额构成、优惠、配送费用与付款方式，然后返回。不得把“页面上出现支付”当作已付款，也不得把“可以看支付页”当作可以实际付款。进入前核实按钮是否会同时提交订单、扣余额或启动支付；未知则记录缺口。禁止实际付款、密码/验证码输入和生物识别确认。未授权的加购、订单创建等限制保持原任务契约；敏感账户或地址信息不进入报告。
