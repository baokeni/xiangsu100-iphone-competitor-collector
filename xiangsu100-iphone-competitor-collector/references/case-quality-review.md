# 用真实案例检查分析质量

在用户要求评估/改进 Skill，或提供学生作业与批注时使用；不是每次普通竞品分析的前置门槛。目标是识别分析哪里看错、漏看或推断过头，并验证修改是否减少这些错误。

## 最小案例包

- 学生原始任务：研究问题、用途（探索/设计决策）、已有范围与授权、使用节奏。
- 原始材料：截图/录屏/文档及来源、日期或未知；保留未删改原件，敏感内容在用于分享前处理。
- AI 原始输出：保留原版，不只留下修改后的成稿；记录 Skill 版本或快照、执行日期，模型未知可明说。
- 老师批注：指出具体句子/页面、为什么不合适、对应证据或判断标准。没有批注仍可自审，但标为 Agent 自审。

用 [案例记录模板](../assets/case-review-template.md) 保存在项目的案例目录。空模板不计为已评测案例，案例内容不写成通用 Skill 默认事实。

## 怎样评

先记录材料里的原始事实，再评分析；引用原图位置/录屏时间/文档页码，不能以“老师觉得不对”替代证据。以下判据逐项用“符合 / 有问题 / 证据不足 / 不适用”，不用凑总分：

| 判据 | 要发现的具体错误 |
|---|---|
| 事实准确 | 误读文字、把标注当界面、建议新增已可见的功能 |
| 流程覆盖 | 漏掉影响结论的返回/取消/分支，或把计划当作已走通 |
| 推断边界 | 从截图直接断言用户失败、原因已确定或效果提升 |
| 比较口径 | 不同对象/条件混比，把未观察写成不存在或更差 |
| 回答问题 | 描述很多页面却未回答研究问题，擅改目标或强迫探索任务改版 |
| 建议适用（按需） | 竞品有优势就要求照搬，未检查目标产品现状、条件和代价 |
| 学生可用性（有记录时） | 学生不知道下一步、看不懂结论、需老师反复补解释 |

每个问题记录原句、来源、问题类型、影响、建议修正；同时保留正确判断，避免一轮修改破坏原有能力。批注存在争议时分别记录老师意见、可核实事实与未解分歧。

## 修改前后怎么比

1. 冻结同一任务和原始材料，保存 Skill 修改前后的快照。除要评估的 Skill 外，尽可能保持执行条件一致；无法保持时记录差异。
2. 重新执行时只提供任务、Skill 和原始材料，不把老师答案塞进生成提示词。批注留给事后评审。若执行者已经看过批注，标“带已知反馈的复跑”，不称为盲测或独立验证。
3. 按同一判据对照原始输出与新输出，给每个问题标“已修正 / 仍存在 / 无法判断”，并单独记录新增错误。没有真正复跑时写“仅规则修订，行为待验证”。
4. 已有案例用于定位错误；有另一份未参与规则修改的材料时，再检查方法能否迁移。一个案例变好不能推出适用于所有题目。

不因为字段完整、测试全绿或措辞更谨慎就认定分析变好。只有实际学生记录才能判断学生是否独立完成；只有相应用户测试才能支持用户效果。授权范围不包含设备/外部操作时，复跑只用已有材料。

没有真实案例时可以准备模板、做明确标为合成的流程演练；结果只能写“流程演练完成，真实案例效果待验证”，不得编造学生、老师批注、复现次数或成绩。
