# 设备环境识别与适配

## 工作方式

先判断本轮是否需要控制设备。已有材料分析、报告修订、设计交接不需要手机驱动。只有当前任务包含真机采集/环境建设，才进入设备适配。Skill名称保留以兼容已有调用，不再将所有用户限定为Mac+iPhone。

默认流程：**识别环境 → 选择已有路线 → 针对缺口研究 → 隔离建设 → 目标App验证 → 正式采集**。检测不匹配后自动进入研究和方案准备；不要求用户自己找技术。不能把“同学跑通过”“官方支持”“模拟通过”“设备连上”合并为本机已适配。

## 先识别、再沟通，在同学电脑上完成适配

Windows、安卓、鸿蒙可以作为优先实施方向。成功案例的原始技术路径暂不可得、教师电脑没有对应设备，都不构成停止适配的理由。已有成功反馈记录为 `user_reported`；AI在同学实际执行环境中依据官方能力重建、排错和验证，取得本机证据后再标记已验证。不能承诺AI能绕过系统限制或解决所有未知问题。

1. **先识别电脑**：使用下方静态检查读取执行主机、架构、工具路径与包版本。区分原生Windows、WSL、远程终端与手机实际连接位置。仅分析材料时跳过此流程。
2. **只补问影响分流的信息**：手机型号、完整系统版本，以及是否连接在当前执行电脑。手机系统来自同学说明或授权发现，不能由电脑系统、华为品牌或“鸿蒙”一词推断。已知信息不重问。
3. **说明路线后继续**：向同学说明“检测到什么、建议哪条路线、AI将配置什么、哪些步骤需要你操作”。缺关键系统信息时等回答；已有环境建设授权则直接执行，不再逐步询问“是否继续”。
4. **AI承担配置和排错**：先自行检查现有证据、工具与权限，再研究对应错误和版本，实施最小修复并复测；按下方低成本排错规则优先代为操作。仅在手机解锁、USB调试授权、安装确认或确需用户完成的权限步骤停下，一次给一个准确动作和成功标志。
5. **实机验证留在同学端**：在同学电脑和目标手机上完成下方最小验证，记录版本、命令结果和证据；教师端本轮只校验规则和模拟，不冒充Windows/安卓/鸿蒙实机验收。

沟通示例（其中Windows须来自实际检查）：

> 已检测到执行电脑是Windows。还需要确认手机型号和“关于本机”中的完整系统版本，以便选择安卓ADB或鸿蒙HDC路线。确认后我会检查和配置工具；手机上的调试授权和安装确认由你完成。连接后先验证目标App截图、页面读取和安全操作，再开始走查。

## 故障时由AI先处理，降低同学操作成本

这项规则适用于所有真机检测和适配路线。**AI先查证并执行能完成的步骤；同学只承担无法代办的必要动作。** 不因出现一次报错就把解决方案搜索、依赖选择、终端命令和日志分析交给同学。

1. **先诊断，再给同学任务**：复用已有设备信息和报错，自己检查路径、版本、执行位置、权限/服务和会话；针对当前错误查本机帮助及官方资料，选有依据的最小修复，在既有授权内执行并复测。信息能从当前工具直接取得时自行读取，不让同学再找同一设置、抄长日志或猜技术原因。确有阻塞信息无法读取时才问一个具体问题。
2. **优先代操作**：先用已有终端、连接器或API完成常规检查、项目内配置和恢复；需要图形界面时，确认已有电脑控制工具确实连接到同学的执行电脑，再按可见当前界面操作允许的步骤。电脑上的普通点击、打开设置页或准备终端可以代办；手机解锁、RSA信任、安装/系统权限确认、账号登录等身份和授权步骤留给本人。沿用当前授权，不每次点击都问“是否继续”；工具不可用时如实说明，不能假装已经远程控制，也不为代操作另行安装陌生远控工具。
3. **必须人工时，一次只做一步**：告诉同学“现在在哪个界面 → 只做什么 → 看到什么算完成”，必要时给一个可直接复制且路径已填好的命令。不要一次抛出整套排错清单，不要求先学ADB、PATH或SDK。收到完成信号后，AI优先自行复查可读结果，再给下一步；界面不一致时只补问当前可见内容，不重复整段教学。新出现的必要人工步骤仍按这一节奏处理。
4. **让等待可理解**：先用一句平实的话说明AI正在处理哪一层，进展较久时简短说明已确认什么和下一步检查什么；给可行动的进展，不只贴原始错误、不断说“失败了”或承诺“马上修好”。没有手机动作需求时明确“我先检查电脑端，你暂时不用操作”。技术细节留在诊断记录，同学看到的提示只包含当前要做的事。
5. **失败后由AI接住**：同学完成一次人工步骤后，继续核对服务、设备、会话及目标App证据，失败则保留首个错误和新结果、调整诊断，不让同学无依据地反复插拔、重装或复制同一命令。没有新证据时停止同一尝试，简要交代已确认状态、最小阻塞和下一条可行路径；不把“请自己查教程”当作交付。电脑控制和普通终端回退同样遵守平台权限，不能规避明确的安全拒绝。

沟通示例（按真实检查结果使用，不预设一定是电脑问题）：

> 当前报错出现在电脑端服务启动，我先检查工具和权限，你暂时不用改手机设置。
>
> 电脑端检查已完成。现在只需要你解锁手机，核对屏幕上的USB调试授权；确认是这台电脑后再允许。看到弹窗消失后回复“已确认”，我来复查连接。

完成标准：诊断/修复由AI承担，必要人工步骤可按当前画面执行，步骤完成后有AI复查证据。规则存在不等于已降低学生实际操作成本；仍需学生端复现验证。

### 环境识别/模拟脚本

```sh
python3 scripts/plan_device_adapter.py inspect --project PROJECT --output adaptation-plan.json
python3 scripts/plan_device_adapter.py simulate --host windows --phone android --tools node adb --output windows-android-plan.json
python3 scripts/plan_device_adapter.py simulate --host windows --phone harmonyos --tools node hdc --output windows-harmonyos-plan.json
python3 scripts/plan_device_adapter.py simulate --host windows --phone ios --ios-major 18 --wda-available --output windows-ios-plan.json
```

Windows可用 `py -3` 代替 `python3`；所有路径相对当前Skill安装目录调整。inspect只读主机类型、架构、PATH中的工具位置、项目文件及包版本，不运行设备命令，不联网、不安装。手机类型必须来自用户说明或已授权的设备发现；默认unknown，不能从Windows推断安卓，也不能从Mac推断iPhone。模拟始终标simulation，不生成采集证据。工具存在不代表版本、驱动、权限或设备已就绪；脚本的 `ready_for_capture` 始终为false，退出码0只表示方案生成成功。

识别的是运行终端所在执行主机。WSL、远程SSH和容器可能返回Linux，继续核对手机在哪台机器、USB由谁持有，不猜测Windows宿主机。多个设备必须明确选择，不能取列表第一个。

手机分类：`android`为安卓，`harmonyos_android`为已确认兼容Android的鸿蒙设备，`harmonyos`为已确认原生鸿蒙，`harmonyos_unknown`为尚未区分的鸿蒙，`ios`为iPhone，`unknown`为未知。未知分类仅补问，不安装两套工具试错。`missing_tools`仅表示静态检查未发现，HDC等工具还可能在SDK目录中，配置前应核对官方环境变量和安装目录。

本包没有 `scripts/bootstrap.py`，不得生成或要求同学运行不存在的“一键安装”命令。Windows运行本Python规划脚本前需确认Python 3可用；缺失时AI仍可通过终端只读检查主机与工具，先完成分流，再按实际需要配置Python，不把脚本本身当作控制手机的驱动。

## 路线矩阵（安卓/鸿蒙文档核对：2026-10-09；非Mac iOS条件保留2026-09-22记录，执行时复核）

|组合|候选技术|此包状态|
|---|---|---|
|Mac+iPhone|现有agent-device 0.20.8 + XCTest封装|有既有工程及历史样本，当前仍需status与目标App验证|
|Mac/Windows/Linux+安卓或已确认Android兼容鸿蒙|优先ADB + agent-device + Snapshot Helper；按所装版本核对主机支持|优先实施路线，安全封装和目标设备验证由AI在同学端完成|
|Mac/Windows/Linux+原生鸿蒙|优先HDC + 支持HarmonyOS的agent-device + ArkUI uitest|官方已列能力子集；需核对主机、系统/API版本与当前设备能力，不套用Android Helper|
|华为/鸿蒙但系统类型未知|先确认型号和完整系统版本|暂不选择ADB/HDC，也不安装工具|
|Windows/Linux+iPhone|满足条件时Appium XCUITest非Mac路线；也可由授权远端执行|有限支持，按下列条件判断，不能一概判定不可行|

Windows/Linux+iPhone的官方有限路线要求iOS/tvOS 18+真机，预装WDA或外部管理的WDA，RemoteXPC通信，以及显式设备ID/系统版本。Windows不能执行默认xcodebuild构建WDA；准备WDA的签名/构建来源需单独说明。`appium-ios-remotexpc`官方文档提示手动安装时至少5.1.0，运行时须重新核对整套兼容版本。缺这些条件时研究学生成功方案或授权Mac执行端，不自动购买云真机、上传登录态或连接陌生远端。

官方来源：

- [agent-device安装与平台依赖](https://oss.callstack.com/agent-device/docs/installation)：Android需要SDK/ADB；本项目已安装包是0.20.8，当前网站文档可能对应更新版本，不直接照抄新命令。
- [Appium UiAutomator2主机要求](https://github.com/appium/appium-uiautomator2-driver#requirements)：Windows/Linux/macOS、SDK及JDK；必须按手机API和驱动版本核对兼容性。
- [XCUITest非Mac主机](https://appium.github.io/appium-xcuitest-driver/latest/guides/non-macos-hosts/)及[版本关系](https://appium.github.io/appium-xcuitest-driver/latest/getting-started/system-requirements/)：有限支持条件。
- [Android ADB](https://developer.android.com/tools/adb)：USB调试、设备授权和指定设备。
- [agent-device鸿蒙能力](https://oss.callstack.com/agent-device/docs/commands#harmonyos-command-boundary)：当前说明列出API 24设备上的HDC/ArkUI能力子集；以所装CLI帮助和所选设备 `capabilities` 为准，不能推断所有HarmonyOS版本支持。
- [Android真机连接](https://developer.android.com/studio/run/device)及[Windows OEM驱动](https://developer.android.com/studio/run/oem-usb)：必要时安装对应USB驱动；USB授权由手机用户完成。
- [agent-device已知限制](https://oss.callstack.com/agent-device/docs/known-limitations)：部分Android设备首次安装Helper需要手机端确认；WSL不能混用Windows的adb.exe和Linux路径。

当前官方移动端安装要求Node.js 22.12及以上，实际配置仍以选定包的 `engines` 为准。HarmonyOS工具可来自官方Command Line Tools或DevEco SDK，先检查已有安装，不能把完整IDE安装当成所有场景的唯一前置条件。HDC、华为HDB与Android ADB是不同通道；开发者模式菜单、是否重启、安装弹窗随系统变化，按照设备实际显示引导。

## AI故障处理与路线切换

Windows + Android或已确认Android兼容鸿蒙的USB异常，先读 [Windows ADB分支诊断](windows-adb-diagnostics.md)。按“执行环境/本地通信 → ADB服务 → 设备列表/Windows接口 → 手机授权 → agent-device会话 → Helper与目标App”分层。电脑端服务失败时不先重复手机设置；服务正常而空列表时，不直接判定驱动损坏。仅当满足该参考的条件时引导一次普通PowerShell初始化，随后回到Codex复查；不默认执行 `adb kill-server`。

每次失败记录执行主机、选定设备、工具/系统/App版本、命令参数（去除敏感内容）、退出码、报错和已完成的检查。按故障所在层采取最小修复：

|故障层|AI处理|何时需要同学操作|
|---|---|---|
|工具/版本|检查可执行路径、Node/SDK兼容性、Windows参数和路径、原生/WSL差异；查官方文档后隔离修复|系统安装权限等实际人工步骤|
|本地服务/执行环境|检查当前权限作用域、ADB路径/版本/服务端点，保留socketpair/daemon原始错误；优先复用兼容健康服务，与设备枚举分开判断|仅平台实际要求的权限授权，或满足条件的一次普通PowerShell对照；明确安全拒绝不能借回退规避|
|连接/授权|区分未发现、offline、unauthorized、多设备；针对性复测，不反复安装驱动|插接数据线、解锁、核对并确认调试授权|
|Helper/页面能力|区分Helper安装失败、HDC/uitest能力缺失和目标App结构稀疏；核对当前版本与capabilities，必要时补适配|设备显示安装确认；目标页面需用户登录时由用户完成|
|执行封装/证据|实现或修复统一接口、实时定位、截图保存和错误返回；复测受影响步骤|任务范围不明确或新操作超出授权|

修复循环为“保留报错 → 定位原因 → 最小修改 → 重跑失败步骤 → 相关回归”。每轮应有新证据或明确修改，同一阻塞无变化时不循环重试。首选路线经诊断有具体不兼容或能力缺失时，再说明依据并评估替代路线：Android可考虑Appium+UiAutomator2；鸿蒙可依据官方HDC/uitest接口隔离补充适配器。不要一开始就安装所有框架，也不要求同学替AI找技术路径。无法自动解决时给出已尝试内容、最小缺口和下一步；材料分析可以继续，但不能静默替代用户要求的真机采集。

## 自动研究与建设边界

1. **复用成功案例**：可获得时记录同学使用的主机OS/架构、手机OS、工具及驱动版本、连接方式、目标App、命令和实际产物。缺详情先记user_reported，继续官方资料研究与当前授权建设，不将口头可行等同已验证，也不因此否定案例或反复索取无法获得的技术路径。
2. **写适配计划**：记录当前组合、推荐后端、版本依据、缺少条件、安装位置、预计会变更什么、人工动作、验证步骤和退出方式。工具版本未知时先检查，不自动安装latest。更换路线前说明具体失败证据及新路线条件，不进行循环猜试。
3. **在当前授权内建设**：用户已要求建设适配环境时，可继续创建独立项目、复用/安装项目内兼容依赖、实现适配器并测试，不反复要求“继续”。仅咨询/模拟时做到计划与离线测试。管理员驱动、设备信任、USB调试授权、签名凭据、系统安全/网络修改等需要的真实用户动作不能代签或跳过；已授权的同一动作无需再次询问。
4. **可恢复执行**：依赖隔离，保留现有工作后端；不自动修改当前 `default_backend`，不禁用支付/授权规则求跑通。发现同一阻塞反复出现且无新证据时停止该尝试，给出最小缺口；不每次失败就换一套框架。
5. **通过后再采集**：记录实际设备/App/工具版本及证据路径，范围只覆盖这组组合。下次版本/设备变化重新检查，不推广成所有安卓或所有Windows均通过。

## 新适配器统一接口与验收

在独立执行工程实现 `status/open/snapshot/screenshot/press/fill/scroll/back/close/finalize`，禁止让模型通过任意shell命令绕开安全封装。Android将package/activity映射到App Card，iOS用bundle ID；保留设备唯一标识、权限、停止词和授权范围。

各后端规范化输出：成功/失败、时间、后端及版本、设备标识、目标App、动作参数、前后状态引用、截图/结构文件路径与哈希、错误和返回证据。未知的可点击性/结构保持unknown，不能默认true；press/fill基于当前观测解析元素，不能跨截图复用坐标或ID。没有页面结构时明确能力降级，只有经复核的当前截图定位才可作为条件路径，禁止盲目固定坐标回放。

最小实机验证：

- 唯一设备可见且用户已授权，目标App可打开；不能只截系统桌面。
- 获取目标App真实截图与结构；证明App/页面身份，而非仅HTTP成功。
- 在明确无副作用的页面完成安全导航、滚动及返回，保存前后证据。
- 支付/下单/验证码等拦截先用离线假事件验证，不在真机点击交易按钮“测试拦截”。观察支付页的授权仍不等于交易授权。
- 正常关闭、连接丢失及重试不丢证据；若本轮允许数据变更，再检查对应回滚，不为验收强行制造数据。
- Windows检查路径空格/中文、UTF-8、命令参数数组及二进制截图写入；不沿用zsh/brew/xcrun命令，不用旧PowerShell文本重定向保存PNG。

适配器的事件/截图只是采集层输出；接回原报告、分支覆盖、来源哈希及当前目标校验，不能因为换了驱动就减少研究验收。

## 当前实现边界

本Skill已提供环境静态识别、Android/鸿蒙路线规划、模拟测试和AI排错建设指导。**脚本是规划器，不是设备执行器**。实际配置、适配器补充和目标App验证由Codex在同学环境中继续完成；无教师端对应硬件不阻止推进。当前包没有这些新组合的完整运行封装或本机实测证明；工具可用、连接建立、目标App验证、研究采集完成分别记录，不混为一个“已完成”。
