# 可选拓展：建立基线与周期对比

仅在用户需要建立长期跟踪基线、比较不同周期/版本或生成周报/月报时启用。Skill 的主要目标是帮助同学跑通一次完整竞品分析；完成一次研究即可，不要求持续跟踪。一次性分析中的不同用户路线，直接在本轮任务计划和报告中记录，不需要 research-snapshot.json，也不需要上期材料。

选择此拓展后的成功标准：能说明某个竞品、某类用户、某条任务路线“之前已知什么、本次发现什么、证据支持到哪、下一步需核对什么”。允许没有变化、没有问题、没有改版建议。仅当需要作设计决定时，转入 cross-report-contract.md；不要为了周报强制制造页面调整。

## 1. 选择周期研究后，建立可复查的基线

从当前研究问题选择长期跟踪产品及关键路线，不追求整款 App 全覆盖。固定平台、用户、路线、检查点编号；记录采集时间、App版本、地区、账号/会员状态、内容样本、设备与语言、入口条件。未知直写 unknown，不填写可识别真实账号的信息。

先登记用户的任务差异：使用目标、知识/经验、约束和成功表现。不同角色只有在这些因素会改变任务路线时才拆开；年龄、职业标签本身不能自动推出操作偏好。依据来自已提供研究时标 documented 并注明来源；推演角色标 hypothesis。角色走查发现的是专家假设，不是实际用户问题发生率。

每条路线记录用户、任务、入口、成功判据，再把入口发现、关键选择、完成反馈、变化/取消、返回及相关异常映射为稳定检查点。只选择与该角色任务有关的分支，沿用 journey-planning.md 的采集要求；不为了覆盖角色操作未经授权的敏感账号或交易。

目录按研究/周期保存 `research-snapshot.json` 与原始材料，例如 `STUDY/cycles/2026-09-28/`。首次建立后保留原件，每周/月用新目录记录；后来修正旧观察时新增修订记录并说明纠正了什么，不覆盖旧历史冒充当时已知。

## 2. 最小快照格式

此 sidecar 不替代原始采集记录，不要求改动单竞品 schema v2。`recorded_at` 是本轮整理/登记时间，用于排序材料周期；`captured_at` 是真实采集时间，未知必须填 `unknown`，不能用整理时间替代。仅知材料周期时不能断言真实改版日期；两期真实采集时间已知但本期并不更新时，标为不可比。以下是**教学样例**，不是实际研究证据；文件与哈希必须换成本轮真实材料。

```json
{
  "kind": "competitor_snapshot", "schema_version": 1,
  "study_id": "reading-study", "cycle_id": "2026-09-28",
  "recorded_at": "2026-09-28T14:00:00+08:00",
  "captured_at": "unknown",
  "research_question": "保存后能否找到原文章并继续阅读？",
  "scope_note": "仅观察指定文章路径；角色为假设，未做真实用户测试",
  "profiles": [{
    "id": "P1", "description": "首次使用，不了解收藏入口位置",
    "basis": "hypothesis", "source_or_assumption": "研究者设定，尚无用户验证"
  }],
  "routes": [{
    "id": "R1", "profile_id": "P1", "task": "保存文章后返回继续阅读",
    "entry": "约定文章详情", "success_criteria": "能够核对保存状态并回到原文章"
  }],
  "observations": [{
    "platform_id": "A", "profile_id": "P1", "route_id": "R1",
    "checkpoint_id": "save-feedback", "status": "observed",
    "app_version": "unknown",
    "conditions": {
      "region": "同一测试地区", "account_state": "登录且非会员",
      "content_sample": "同一文章或预先定义的同等条件样本",
      "device": "同一设备及系统", "locale": "zh-CN",
      "entry_condition": "从文章列表进入详情"
    },
    "facts": {"feedback": "显示已保存文字"},
    "limits": "只观察到反馈，是否被用户理解待验证",
    "evidence": [{"path": "sources/save.png", "sha256": "实际原件SHA256"}]
  }]
}
```

观察状态为 observed/not_verified/blocked/excluded。未采到的检查点保留编号、条件与缺口，facts填 `{}`、evidence填 `[]`；不要把上期截图登记为本次证据。局部观察拆成更细检查点，避免一处可见就把整条路线标为完成。facts 只放已复核的界面/行为事实，解释、可能原因和建议放在报告正文，不能混进事实对比。

## 3. 下期如何比较

先复用基线定义和关键检查点；用户、任务或样本范围改变时分别说明，不能把口径变化归因于产品改动。增量采集不强制重走全部 App；未复查项必须可见。预算优先留给上期问题、决策关键路径和新变化的相关分支。

```sh
# 首期：验证快照及其来源，不启动设备
python3 SKILL_DIR/scripts/compare_research_cycles.py --current STUDY/cycles/FIRST/research-snapshot.json
# 后续：输出 JSON、Markdown 和可打开 HTML；不覆盖两期原件
python3 SKILL_DIR/scripts/compare_research_cycles.py --baseline STUDY/cycles/FIRST/research-snapshot.json --current STUDY/cycles/NEXT/research-snapshot.json --output-dir STUDY/comparisons/FIRST-to-NEXT
```

工具对稳定编号和已登记事实进行比较，**不自动识别截图变化或判断改版原因**：

|结果|如何解释|
|---|---|
|候选变化|同条件下记录不同；打开两期原件，排除描述方式、动态内容、促销、账号分群或灰度因素，再确认具体差异|
|已观察项一致|只代表本轮检查点的已登记事实一致，不表示整个产品没改|
|新增观察范围|这次首次看到，不能直接说是产品新上线|
|本次未复查/证据不足|不能判断变更，也不能写功能被删除|
|条件不同或未知|地区、账号、样本、用户定义、路线等不一致；先对齐或明确分开分析|

App版本变化单独保留，不是界面变化的充分证据。文件哈希只查原件完整性；时间、动画或图片换了一张不自动算改版。同一平台不同角色的差异按角色条件解释，不混作跨期改版。版本不明时尤其不能断言全量上线时间。

## 4. 周报/月报与目标建议

交付先给本期问题、基线与当前周期、已复查/未复查范围，再逐项给“原来 → 现在 → 两期证据 → 适用用户与路线 → 确认状态 → 可能影响（推断）→ 下一步”。确认差异后按信息、交互、规则、内容或视觉变化描述，不自动提升为效果。保留变化候选、已确认局部差异、条件性差异、未验证的区别；语义复核人的身份、时间和说明写在报告里，工具输出仍叫候选清单。

用户方向可以质疑但不直接推翻：保留原话与当前方向，另外列出“证据引发的疑问—替代解释—建议如何验证/调整—待用户接受”。例如信任方向中观察到价格条件难懂，可建议增加费用理解检查，但不擅自删除信任目标。未接受调整时沿原范围做有依据的分析，同时保留异议和未知。

有差异不必跟进改版：下一步可以继续观察、补证、保留现状或启动设计分析。定期研究能力不等于已有定时运行；只有用户实际要求设置周期任务时，才使用可用调度工具并确认研究范围、时间及运行条件。不得宣称写入本规则后已经每周/月自动采集。
